# 基准对照：确定性门 vs 朴素判定（2026-11-18）

## 为什么做这件事

"确定性判决优于'让模型看着办'"是主张，不是证据。最便宜的检验方式：把同一个朴素替代品放到同一批输入上，数分。

脚本：`benchmarks/adversarial_baseline.py`（纯标准库，无网络，无模型调用）。已接入 CI，每次推送自动跑。

## 对照组怎么定义

朴素判定器被写成"最可能的偷懒实现"，不是稻草人：

```
JSON 里出现 class1 / severe / life_threatening → reject
requires_submission 为真，或文本里出现 intended_use → hold
其余 → go
```

这大致就是"直接 grep 一下 JSON"会得到的判据，也是模型在没有规则表时容易收敛到的直觉。

探针的期望判决由判定器自身文档化的语义固定，不是事后按结果编的。

## 朴素法错在哪（两类，方向相反）

1. **该拦的放行（4 条）**：空证据、未知变更类型、未知安全等级、把字符串 `"yes"` 当作等价声明。这四条的共同点——**没有被枚举校验，也没有被"未证明即不放行"覆盖**。
2. **该放的拦住（3 条）**：PCCP 绿色案件被误判 hold，因为 JSON 里出现了键名 `affects_intended_use`（值其实是 `false`）。**按字面匹配键名与按语义取值，是两件事**；朴素法分不清。

这正是 LGD 三条律在代码里的落点：
- 有籍（registered）＝每条判决必须能被规则表定位，未知不是默认可放行；
- 有证（evidenced）＝go 必须有证据引用，空 ref 不算证据；
- 有门禁（gated）＝critical 一票否决，且不允许被后续规则降级。

## 这条基准的边界（不夸大）

- 12 条探针规模小，验证的是**语义正确性**，不是统计显著性；
- 对照对象是"朴素关键词法"，不是"某家商用产品"，我们没有任何商用模型的实测成绩，不编；
- 朴素法也能通过 5 条（其中 2 条是它真的判对了，3 条是碰巧落在同一判决上）；
- 判断"哪条探针该是什么判决"本身由我们定义，这是循环的一部分——所以每条期望都在文档里写明理由，欢迎外部人用他们的口径重写探针再跑。

## 怎么复跑

```bash
python benchmarks/adversarial_baseline.py

```
