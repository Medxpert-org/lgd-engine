# lgd-engine 可行性与架构设计（2026-11-18）

## 一、先给定性：可行，但要砍掉一半野心

现在的仓库已经不是一个 PPT 概念：它有能跑的门禁引擎、两个判定器、本地记忆、CLI、MCP 服务器、REST 与 SSE 两个演示面、9 步 CI，以及本轮新增的 13 条契约断言。全部零第三方依赖，`python -m unittest discover -s tests` 一秒内跑完。

可以下这个结论：**"把判定规则做成可执行的门禁"这条技术路线已被自证可行**，因为最小闭环已经在跑，且它的失败模式（判定器崩溃、无证据放行、越权调用）都被断言钉住了。

不能下的结论是：**"13 域企业级平台"现在不存在**。仓库里 `lgd_engine/judges/` 只有两个判定器，README 自己也写着 "2 shipped: 510(k), post-market"。13 域是一张对齐图谱（`demo1/test_ecosystem.py` 测的是图谱对齐，不是 13 个判定器）。把图谱说成平台，是这份设计首先要拒绝的事。

所以可行性判断分两段：

| 命题 | 判断 | 依据 |
|---|---|---|
| 判定可执行化 | **已成立** | 引擎 + 2 判定器 + 13 条断言全绿 |
| 13 域全覆盖 | **未成立，且不该一次做完** | 只有 2 个判定器；每域需要独立的法规依据与黄金用例 |
| 企业级多租户/权限/审计 | **未成立** | RBAC 表存在但无特权角色（见第四节） |

## 二、目标架构：五层，各层只做一件事

```
L4 接入面   CLI · MCP(stdio) · REST(/v1) · SSE(会话) —— 同一份 GateReport
L3 记忆与证据  LocalMemory(append-only) · 证据引用 · 审计留痕
L2 判定器   DomainJudge × N  —— 每域一策，只回答"这域怎么看"
L1 律引擎   GateEngine —— 聚合、L1/L2/L3 三律、fail-safe
L0 契约     laws.yaml · jurisdictions.yaml · openapi.yaml
```

四条设计约束，从现有代码里长出来，不是新发明的：

1. **引擎不写库**。`GateEngine` 是纯函数：进 ctx，出 GateReport，落库由调用方做。这条已经在代码注释里写死（"engine itself does not write, keeps it pure & testable"），必须保持。
2. **判定器只答本域**。`DomainJudge` 不关心最终裁决，只给 verdict + reasons + evidence；跨域冲突由 L1 解决。否则域一多就互相打架。
3. **三律在引擎层强制，不在判定器层**。L3（任一 critical → reject）、L2（无证据的 go → hold）、L1（调用方负责记录）全部集中在 `GateEngine.evaluate()`。判定器只标 level，不做最终判定——这条已经实现，且被断言覆盖。
4. **工具故障 ≠ 判定拒绝**。判定器崩溃时 verdict 是 reject（fail-safe），但 `errors` 必须非空，CLI 退出码 3 而不是 2。这条是本轮断言钉住的，也是外部审查最容易挑的点：一个坏安装不该读成一次合法否决。

## 三、判定器怎么扩到 13 域：一条可验证的流水线

每加一个域，必须同时交付四件东西，缺一件就不算实现：

| 交付物 | 作用 | 拒绝理由示例 |
|---|---|---|
| `judge_<domain>.py` | 该域规则 | 只有关键词匹配，没有可枚举的 rule id |
| 规则表（rule id → level） | 可审计 | level 随手标，同一情形两次判定不一致 |
| 黄金用例 ≥5（含 1 个 expected_verdict） | 可复跑 | 用例只有正例，没有反例 |
| 证据要求声明 | L2 可执行 | 允许无证据 go，靠调用方自觉 |

这条流水线的价值不在"快"，而在**每个域都能被同一个尺子量**：`--all <cases>` 全命中才算过，漂移即红。现在 2 个域做到了，另外 11 个域没有。

排序建议（按"规则可枚举程度"而非商业热度）：510(k)（已有） → post-market（已有） → 标签/说明书 → 变更控制 → 供应商变更 → 不良事件报告 → 其余。理由：越靠前的域，规则越接近"可写成 if-else"，越靠后的域越依赖人的判断，硬编码会产出假确定性——那是比不做更危险的事。

## 四、必须写进文档的四个缺口

**缺口 1：RBAC 是空架子（已于同日闭合）。** 原状：`ROLE_TOOLS` 里 `reviewer` 与 `read-only` 工具集完全相同，且没有任何写/审批类工具。当日处理：把"审批"的最窄语义定为**只追加、可追溯的签核记录**（`record_decision`：case_id + verdict + rationale 必填，写入审计），`reviewer` = 只读集 + 该工具；`read-only` 调用它一律 `-32003`。验证方式：契约测试断言"reviewer 是 read-only 的严格超集且差集恰为 `record_decision`"、双向调用各一条；MCP 冒烟测试同时跑"只读被拒 / reviewer 通过"两个方向。留待 v0.3 的是更强的审批语义（多级复核、双人签核），不是权限本身。

**缺口 2：契约跑在实现前面。** `docs/openapi.yaml` 冻结的是 `/v1/judge`、`/v1/decisions`，而实际可跑的是 `demo1/web.py` 的 `/judge`（无 `/v1` 前缀）。README 已诚实标注，但外部读者第一眼看到的是 OpenAPI，会以为 `/v1` 可用。

**缺口 3：只有 SQLite 本地记忆。** 单机 append-only 够用于演示与自证，不够用于多租户。企业级要的是可查询的决策账本（谁、何时、依据哪条、证据在哪），这部分现在只有一个 `localmem_min`。

**缺口 4：TS 与 Python 双实现并存。** `lgd-engine-ts` 与 `lgd_engine` 各有一套。双实现的风险不是维护成本，而是**同一输入两种判定**——这会直接摧毁"可复现"这个唯一卖点。要么让 TS 侧只做客户端，要么加一个跨实现一致性测试。

## 五、到 v1.0 的最小路径（不做平台的平台）

| 阶段 | 内容 | 完成判据 |
|---|---|---|
| v0.2（本周可做） | 第 3–5 个判定器 + 各自黄金用例 | `--all` 全命中，CI 绿 |
| v0.3 | 真实特权角色 + 审批留痕（先定语义，再写代码） | 越权调用被拒且进审计；审批动作可追溯 |
| v0.4 | `/v1` 与实现对齐（或把 OpenAPI 降级为草案） | 契约里每条 path 都有可跑实现，或被显式标注 draft |
| v0.5 | 决策账本（SQLite → 可查询结构，含导出） | 能回答"某次 reject 依据哪条规则、证据是什么" |
| v1.0 | 跨实现一致性测试 + 外部人独立复跑报告 | 外人 clone 后一条命令跑通，且结论与我一致 |

## 六、诚实的竞争位置

这个仓库真正的差异点不是"判定器多"，而是**判定本身可被机器复核**：同一 ctx 两次跑结果逐字节相同，判定器崩了会自己承认，规则触发有 id 可查。同品类工具多数交付一段提示词或一张打分表，交付不了"可复跑的裁决"。

但这也意味着：**判定器数量不是护城河，可信度才是**。13 个域各写半页规则、彼此矛盾，反而不如 2 个域做到可复跑。这一点如果不写进 README，将来一定有人拿"只有 2 个域"来质疑——而那时我们唯一能拿出来的回答，是"是的，只有 2 个，但每一个都能被你复跑"。

## 七、本轮没做的事

- 没有新增判定器（加域需要法规依据与黄金用例，不能凭空写）
- 没有改 RBAC 语义（属产品决策）
- 没有推送仓库（对外动作需授权）
- 没有跑 TS 子项目测试

以上四项都不在本轮范围内，写清是为了让后来的人知道边界在哪，而不是以为遗漏。
